# 项目维护流程

适用于代码、教学规则、教材和目录维护。AGENTS 负责任务路由；本页只负责改动如何交付。小修改用实际 diff 和检查结果即可，不为每次改字新建计划、报告或工具。

## 长期目标：清爽

2026-10-14 用户确认。“清爽”指职责明确、入口好找、规则只有一个维护源、结果可回查证据；不以文件数量少为目标。学习内容追求优雅、简单，项目维护也遵循这一原则。

- 用户入口围绕 Chunks、Shadowing、词汇；后台按获取、编纂、教学、记录与评估等工作职责组织，不把功能块和代码／Skill／prompt等承载方式各建成一套目录体系。
- 一项任务有一个权威入口：AGENTS 指路，Skill 定流程，prompt 给专门任务，代码做机械操作，文档供人阅读；相同规则不在多个位置独立维护。
- 资产、规则和记录分开：原材料／教材／题目是资产，执行方法是规则，来源／原答／反馈是记录。教材完成、材料数量和跟读完成不能冒充能力证据。
- 先使用现有材料与流程，再根据真实问题调整；没有实际需求不新建数据库、评估系统、分类、工具或空计划。小改动不增加维护仪式，历史优先回查 Git。
- 简化时收拢重复入口和退出使用的产物，保留有用知识、当前依赖、原件与真实证据。修改目录前先看最新文件，前端分类与文件系统一致。

每次扩充或整理都问：

1. 要做一件事，能否马上找到入口？
2. 改一条规则，是否只需改一个地方？
3. 看一个结果，能否回查材料或练习证据？

三个问题答不清时，优先修职责与引用，再考虑增加文件或功能。

## 从请求到提交

1. **定范围**：读当前文件和 Git 状态，确认用户要改变的行为、涉及资产、验收条件。记录既有改动；不回滚不明来源工作。多步改动在对应 engineering/design 文档写简短清单。
2. **找规则源**：按 AGENTS 路由修改唯一源。概览只保留用途与链接；有生成器时同时检查输入与输出，不仅手改生成页。
3. **实施**：保留原材料、源 ID、引文与实际原答；移动要更新引用、导航、公开清单及旧链接映射。删工具先找调用与核验依赖。能力判断须能回查任务、日期和提示情况。
4. **审查**：读最终 diff，核范围、遗漏、规则冲突、失效链接、隐私与发布边界。材料编写完成、学习掌握、本地通过、线上发布分别报告；代码改动核失败路径和现有行为。需要独立审查时在授权范围使用，不以自查冒称独立审查。
5. **验证**：按下表选择检查，失败先修再跑相关项。测试只证明其实际覆盖的行为；语料校验不证明无遗漏或用法全部正确。
6. **提交**：查看 staged diff 与文件清单，确保仅包含本次授权范围，提交后核 commit 和工作区。Git 保留历史，不另堆废弃副本。不把忽略的原材料当作已纳入提交。
7. **发布与使用**：push／发布按当前用户授权执行；首次发布核公开清单。发布后看 Actions 和网站，不能用本地测试替代上线证据。实际学习试用必须有用户参与，无原答不生成练习结果。

## 按变更选择验证

| 变更 | 最低检查 |
|---|---|
| 小段文案 | 语义、原句与链接，git diff --check |
| 教学规则／Skill | 入口和相对链接、执行源一致性；改 Skill 跑 quick_validate |
| 教材提取／生成 | 源文件存在／哈希、原句定位、条目数和 ID、必要语义审校；输出与生成器一致 |
| 目录迁移／清理 | 当前引用、nav 与实际父目录、公开范围、旧深链；服务端与浏览器回归 |
| 阅读器行为 | 服务端测试、桌面回归和相关移动测试、静态构建 |
| 发布配置 | 干净检出下的 CI 检查与静态构建；实际发布再核部署结果 |

运行命令与环境依赖以 [site/README](../site/README.md) 为准，不在本页复制。素材获取验收以 [资料手册](../materials/HANDBOOK.md) 为准。

## 证据存在哪里

设计与范围写 engineering/design/；有实质范围或风险的交付检查写 engineering/verification/；内容变化写 CHANGELOG；原答写 progress/，当前学习状态仅作带链接的摘要。报告至少写改了什么、实际检查、结论边界与未做事项，不复制原数据或生成第二套规则。

提交是一个可回退的稳定版本。需要撤销已提交改动时使用明确目标的 Git revert，避免 reset 覆盖之后的工作。用户不要求 push 时停在本地提交，交付说明列 commit、验证和限制。
